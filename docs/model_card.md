## Limitations and known risks

- **The label delay is not solvable by modelling.** The monitor can flag an attack the day it starts, but a *retrained* model still waits ~60 days for chargebacks to mature. The gap is covered operationally — see `docs/runbook.md`.
- **Merchant reputation points the wrong way during an attack.** A newly attacked merchant looks clean because its fraud has not been reported yet. The feature is kept (a tree model handles the non-monotonicity) and documented rather than silently dropped (`docs/feature_pipeline.md`).
- **Segment thresholds encode a cost model, not a moral judgement.** If the assumed cost of a false decline is wrong — for example, if declining a customer causes harm the $ figure does not capture — the thresholds are wrong too. The cost model is a small JSON file precisely so it can be challenged and re-tuned without retraining.
- **This model is trained on synthetic data** generated for this project. The engineering is production-shaped; the numbers are not a claim about any real portfolio.
- **Rare-event metrics are noisy.** PR-AUC on a window with few frauds moves a lot; that is why promotion requires a minimum number of positives.

## Fairness and ethical considerations

- The model uses transaction and merchant behaviour only. It does not consume demographic attributes, and no proxy for them was engineered.
- A false decline is a real harm to a real customer, which is why it carries an explicit cost and why the policy is measured on the false-decline rate, not only on fraud caught.
- Every decision ships **reason codes** (per-feature contributions), so an adverse outcome can be explained rather than asserted.
- Per-channel performance is tracked and a promotion is blocked if any channel regresses — an average must not improve at one group's expense.
